הפרדת אחריות עיקרית — צוות ההרשאות מיישם בקשות ומשייך Identity, Role, Model Profile ו-Usage Profile. צוות ההרשאות אינו קובע את גובה התקציב — זו סמכות Budget Owner / Allocation Manager בלבד.
1

הגדרות מרכזיות

Organizational Unit

חטיבה (ובטכנולוגיה — גם תחום). קובע מאיזה Pool תנוכה העלות. כל עובד שייך לחטיבה ראשית אחת.

Role

מגדיר מה המשתמש יכול לראות ולנהל במערכת. אינו קובע מודלים או תקציב.

Model Profile

קובע לאילו מודלים ויכולות המשתמש רשאי לגשת (Standard / Advanced / Developer / Restricted).

Usage Profile

קובע את הקצאת ברירת המחדל החודשית (Basic / Standard / Power / Custom). ניתן לשינוי על ידי גורם תקציבי.

Budget Override

חריגה / הגדלה מעבר לברירת המחדל של Usage Profile, עבור עובד ספציפי. מבוצע רק על ידי Budget Owner / Allocation Manager, בתוך ה-Pool החטיבתי.

Provisioning

הפעולה הטכנית של שיוך Identity + Role + Profiles. מבוצעת על ידי צוות הפלטפורמה לאחר אישור מנהל מורשה.

2

תפקידים ואחריות בתהליך

תפקיד מה הוא עושה בנוהל זה יכול לאשר פתיחה יכול לקבוע תקציב מיישם טכנית
Central Admin ניהול כלל ההיררכיה, העברת תקציב בין חטיבות, אישור חריגים ארגוניים כן — כלל הארגון כן — ארגון + חטיבות כן
Division Budget Owner אישור פתיחת משתמשים בחטיבה, הקצאת Budget ברמת עובד, האצלה ל-Allocation Managers כן — בחטיבה שלו כן — בתוך ה-Pool שלו לא
Domain Budget Manager אישור פתיחת משתמשים בתחום (טכנולוגיה), הקצאת תקציב בתחום כן — בתחום שלו כן — בגבולות ה-Allocation לא
Allocation Manager ניהול שוטף של קבוצת משתמשים, שיוך Profiles, עריכת הקצאות בגבולות שהוגדרו כן — בקבוצה שלו כן — בגבולות שהוגדרו לא
צוות פלטפורמה ביצוע טכני של הבקשה: שיוך Identity, Role, Profiles במערכת. אינו קובע תקציב לא לא כן
3

תרחישים ותהליכים

1

פתיחת משתמש חדש

עובד חדש בארגון, או עובד קיים שנכנס לקבוצת המשתמשים המורשים של Claude.
1
Division Budget Owner / Allocation Manager
מזהה צורך בפתיחת גישה לעובד ומאשר את הבקשה.
הגורם המאשר חייב להיות מורשה לאוכלוסייה שאליה שייך העובד.
2
Division Budget Owner / Allocation Manager — החלטות נדרשות
מגדיר 4 פרמטרים לבקשה:
א. Organizational Unit — חטיבה + תחום (בטכנולוגיה)
ב. Role — End User / Allocation Manager / אחר
ג. Model Profile — Standard / Advanced / Developer / Restricted
ד. Usage Profile — Basic / Standard / Power / Custom
3
Division Budget Owner / Allocation Manager — אופציונלי
Budget Override — אם נדרשת הקצאה שונה מברירת מחדל ה-Usage Profile.
Override מבוצע רק בגבולות ה-Pool החטיבתי. מתועד ב-Audit Log.
4
צוות פלטפורמה
מקבל את הבקשה עם כל הפרמטרים ומיישם: שיוך Identity, Role, Model Profile, Usage Profile.
צוות הפלטפורמה אינו קובע ואינו משנה תקציב — מיישם בלבד.
5
מערכת — אוטומטי
הגישה פעילה. צריכת המשתמש נרשמת ומצטברת לחטיבה ול-Budget הרלוונטי.
2

מעבר עובד בין חטיבות

עובד עובר יחידה ארגונית — השיוך, העלות וההרשאות צריכים לעבור בהתאם.
1
Division Budget Owner (חטיבה החדשה) / HR / מנהל ישיר
מגיש בקשת שינוי שיוך: שם עובד, חטיבה ישנה, חטיבה חדשה, תחום חדש (אם רלוונטי).
2
Division Budget Owner (חטיבה החדשה) — החלטה נדרשת
מגדיר Role, Model Profile ו-Usage Profile בחטיבה החדשה — לא בהכרח זהים לחטיבה הישנה.
3
צוות פלטפורמה
מעדכן את שיוך הישות הארגונית, ה-Role וה-Profiles. הצריכה העתידית נרשמת לחטיבה החדשה.
שינוי השיוך נרשם ב-Audit Log עם תאריך השינוי.
4
מערכת — אוטומטי
מהתאריך הקובע — הצריכה נרשמת לחטיבה החדשה. היסטוריית החטיבה הישנה נשמרת לצורכי דיווח.
מקרה מיוחד — מימון צולב בין חטיבות: אם חטיבה א׳ רוצה לממן עובד בחטיבה ב׳ (לדוגמה, תפעול מממנת עבודת פיתוח בטכנולוגיה) — Central Admin מסיט תקציב מחטיבה א׳ לחטיבה ב׳, ואז Division Budget Owner של חטיבה ב׳ מקצה לעובד הרלוונטי מה-Pool שלו. העובד עצמו לא עובר חטיבה — רק התקציב מוסט.
3

הגדלת מכסה / Budget Override

עובד מגיע לגבול הקצאתו ומבקש הגדלה, או מנהל מזהה צורך מראש.
1
End User / מנהל ישיר
מגיש בקשת הגדלת מכסה ל-Allocation Manager / Division Budget Owner של החטיבה.
ניתן לבקש גם יזום על ידי מנהל, ללא בקשת העובד.
2
Division Budget Owner / Allocation Manager — בדיקה ואישור
בודק: האם יש יתרה ב-Pool החטיבתי? אם כן — יכול לאשר ישירות.
יש יתרה ב-Pool

Division Budget Owner / Allocation Manager מאשר את ה-Override ישירות מה-Pool שלו. לא נדרש אישור Central Admin.

אין יתרה ב-Pool

בקשת הגדלת תקציב חטיבתי מועלית ל-Central Admin. Central Admin מחליט על הגדלה קבועה / חד-פעמית.

3
צוות פלטפורמה
מיישם את ה-Override בפרופיל המשתמש לפי ההחלטה המאושרת.
4
מערכת — אוטומטי
ה-Override נרשם ב-Audit Log: מי אישר, סכום, תאריך, נימוק.
Override לעובד ≠ שינוי ה-Usage Profile הארגוני — ה-Override הוא פרטני לעובד בלבד ואינו משפיע על ברירת המחדל לשאר המשתמשים עם אותו פרופיל.
4

עזיבת עובד / הסרת גישה

עובד עוזב את הארגון או מסיים תפקיד שדורש גישה לפלטפורמה.
1
HR / מנהל ישיר / Division Budget Owner
מגיש בקשת הסרת גישה עם שם העובד ותאריך תחילת תוקף.
2
צוות פלטפורמה
מנתק את שיוך ה-Identity ומשבית את הגישה. מתעד ב-Audit Log.
נתוני ההיסטוריה והצריכה של העובד נשמרים — לא נמחקים.
3
מערכת — אוטומטי
יתרת ה-Budget שהוקצתה לעובד חוזרת ל-Pool החטיבתי — זמינה להקצאה חדשה.
תזכורת: עובד ב-Offboarding שהיה בעל Role ניהולי (Allocation Manager וכדומה) — יש לוודא גם הסרת ה-Role הניהולי בנפרד לפני השבתת הגישה, כדי שהאצלת הסמכויות שלו תתעדכן.
4

טבלת Provisioning — Source of Truth לבקשות פתיחה ושינוי

הטבלה משמשת לניהול בקשות פתיחה ושינוי. לאחר אישור ומילוי כל השדות — היא מועברת לצוות הפלטפורמה לביצוע. שדות מסומנים בכוכבית (*) הם חובה.

אפשרויות Role
  • End User
  • Allocation Manager
  • Domain Budget Manager
  • Division Budget Owner
  • Central Admin
אפשרויות Model Profile
  • Standard — גישה למודלים בסיסיים
  • Advanced — גישה למודלים מתקדמים
  • Developer — כלי קוד ו-Agents
  • Restricted — גישה מצומצמת
אפשרויות Usage Profile
פרופיל מתאים ל הקצאה חודשית מי יכול להקצות
Basic שימוש מינימלי / ניסיוני להשלמה Allocation Manager
Standard Usage משתמש שוטף להשלמה Allocation Manager
Power שימוש אינטנסיבי להשלמה Budget Owner
Custom חריג לפי צורך עסקי לפי החלטה Budget Owner בהתאם לסמכות

* ערכי ה-Baseline הכספיים לכל פרופיל יועברו בטבלה נפרדת.
