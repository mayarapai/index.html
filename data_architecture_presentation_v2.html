Full-Load ETL — אין CDC
Informatica מריץ batch לילי. אין Change Data Capture ארגוני. כשהתהליך נופל — אין recovery נקי ואי אפשר להריץ מחדש ללא סיכון לליבה
DWH ספריים — אין Unified Model
כל עולם מוצרי (אלמנטר, פנסיה, השקעות) מנהל DWH נפרד עם schema שונה. אין data model ארגוני אחיד, אין shared entities
Core Coupling — תלות מלאה
BI, דיגיטל ושירות מושכים ישירות מהליבה. עומס על ה-core, latency גבוה, סיכון תפעולי. אין הפרדה בין source לבין consumption
אין Serving Layer — אין ODS
מוקדים ודיגיטל עובדים עם snapshots מיושנים. אין API-first serving layer, אין low-latency read path. פתרונות נקודתיים לכל מערכת
אין Golden Record — MDM מפוזר
MDM-ים נפרדים לפי עולם מוצרי + MDM לסוכנים. אין identity resolution ארגוני, אין Golden Customer ID, duplicate records בלתי מנוהלים
Business Logic בתוך הליבה
חישובים כמו פדיון פנסיה רצים ב-core systems. כל שינוי = release cycle מלא + סיכון regression. לא ניתן לנפות לוגיקה ל-data layer
אין Feature Store, אין ML Platform מנוהל, אין AI Foundation
Dataiku On-Prem פועל בצורה מצוינת לאנליטיקה וML, אך אין Feature Store מנוהל, אין MLOps pipeline, ואין חיבור מסודר ל-data products. כל מודל מושך feature-ים בדרך שלו

Design Principles של הארכיטקטורה
ששת העקרונות שמנחים כל החלטה ארכיטקטונית בפלטפורמה
Separation of Core & Consumption
מערכות ה-core נשארות מקור תפעולי — לא מקור צריכה. כל BI, AI, דיגיטל ושירות צורכים מ-Lakehouse/ODS בלבד. מסלול: Core → CDC → Bronze → Gold/ODS
Layered Architecture — Single Responsibility
כל שכבה אחראית על תפקיד אחד: Lakehouse מעבד, MDM מזהה, ODS משרת, Customer Profile מחבר, CDP מפעיל. אין cross-layer leakage של לוגיקה
Event-Driven by Design
מעבר מ-Batch-first ל-Event-first: שינויים בליבה מזרימים events לפלטפורמה. CDC → Kafka → downstream consumers. מפחית latency, מאפשר triggering ו-activation בזמן אמת
Data Products — לא טבלאות
כל ישות עסקית = Data Product עם owner, SLA, data quality rules, lineage, ו-API contract. Customer Product, Policy Product, Claim Product — לא flat tables
Hybrid by Design
לא הכל בענן, לא הכל On-Prem. כל רכיב ממוקם לפי: עלות compute, latency, רגישות דאטה, proximity לליבה. Dataiku On-Prem נשאר לML training. GenAI — ענן מנוהל
AI Natively Integrated
AI לא מעקף את ארכיטקטורת הדאטה — הוא נשען עליה. Feature Store מ-Gold, profiles מ-Customer Profile, knowledge מ-Vector Store. אין "shadow data" ל-AI
McKinsey Rewiring Framework
היתרון הארגוני העתידי לא ינבע מהטמעת מודלי AI בלבד, אלא מהיכולת לבנות פלטפורמות, מודלים תפעוליים ויכולות ארגוניות שמאפשרים ל-AI לעבוד בסקייל, במהירות ובצורה חוזרת.

Bronze
Raw Landing — as-is from source

  • אין business logic, אין joins, אין אגרגציות

  • חיבור ראשוני בין sources — foreign key resolution

MDM
MDM & Identity Resolution Layer
שכבת הזהות הארגונית — מי הישות, מה המזהה הגולדן שלה, ומה הקשרים בינה לבין ישויות אחרות
מה MDM עושה — ומה לא
תפקידכן / לא
Identity Resolution — איחוד duplicatesכן
Golden ID (cross-system unique key)כן
Entity Graph — קשרים ותפקידיםכן
Contact master (phone, email, address)כן*
היסטוריה עסקית — פוליסות, תביעותלא
Customer 360 / Profile מלאלא
Scores, segments, AI outputsלא
* בהתאם למדיניות רגולטורית ואבטחת מידע
אתגר ביטוחי ספציפי
בביטוח אין 1:1 בין אדם לפוליסה. אב = policy holder, בן = insured. MDM חייב לנהל entity graph עם role_type לכל קשר: POLICY_HOLDER, INSURED, PAYER, BENEFICIARY, AGENT
מודל ישויות — Entity Graph (simplified)
CUSTOMER(customer_id, id_number, type, status)
 ├─ CUSTOMER_IDENTIFIER(type, value, source, is_primary)
 ├─ CUSTOMER_CONTACT(type, value, verified, primary)
 └─ CONSENT(type, status, updated_at)

POLICY(policy_id, product_domain, status, premium)
CLAIM(claim_id, policy_id, type, status, amount)
AGENT(agent_id, name, type, status)

CUSTOMER_POLICY_REL(customer_id, policy_id, role_type, valid_from/to)
CUSTOMER_CLAIM_REL(customer_id, claim_id, role_type, valid_from/to)
POLICY_AGENT_REL(policy_id, agent_id, role_type, valid_from/to)
מצב קיים vs יעד MDM
קיים: MDM-ים מוצריים נפרדים, MDM סוכנים בנפרד, אין Golden ID ארגוני
יעד: MDM ארגוני אחד (federated but centrally governed), Golden ID, entity graph מנוהל, feed לכל שכבות הפלטפורמה
ODS
ODS — Operational Data Store & Serving Layer
שכבת ה-Serving התפעולית — מספקת snapshot עדכני בזמן-קרוב-לאמת לכל מערכות הקצה
מה נמצא ב-ODS
  • ✓ Current-state snapshot ללקוח, פוליסה, תביעה
  • ✓ פוליסות פעילות וסטטוסים תפעוליים
  • ✓ Open claims ואינדיקציות שירות
  • ✓ פרטי קשר עדכניים (מ-MDM master)
  • ✓ Service flags ו-customer alerts
  • ✗ היסטוריה מלאה — זה ב-Lakehouse
  • ✗ Heavy analytics — זה ב-Gold
  • ✗ ML inference — זה ב-AI Platform
Guiding Principle
"Lakehouse חושב — ODS מגיב"
ODS מותאם ל-read path מהיר: עשרות ms latency, high concurrency, API-first. לא למשימות ETL כבדות
נושאLakehouse / GoldODS
מטרהעיבוד + היסטוריהServing תפעולי
Update frequencyBatch / micro-batchNear real-time / streaming
Read latencyשניות עד דקות<100ms (API)
ConsumersBI, AI, Analyticsמוקדים, דיגיטל, CRM
Data scopeFull historicalCurrent snapshot
Storage typeObject store (S3/ADLS)Operational DB / Cache
Tech examplesDatabricks, SparkPostgreSQL, Redis, Elasticsearch
ODS Design Principles
  • → API-first exposure — REST / GraphQL
  • → Incremental updates from Gold (Change Feed)
  • → SLA per entity: latency SLA + freshness SLA
  • → Read-write separation — ODS הוא read-only
  • → Cache layer (Redis) לפרופילים שנטענים בתדירות גבוהה
Customer Profile
Customer Profile / Customer 360
שכבת החיבור — לא מקור דאטה, אלא composition layer שמאחד זהות, היסטוריה, מצב ותובנות לפעולה עסקית
מה מרכיב את Customer Profile
שכבת מקורמה היא תורמת
MDMGolden ID, identity, relationships, roles
Gold (Lakehouse)History, policies, claims, value, KPIs
ODSCurrent state, active policies, open cases
AI / ModelsChurn score, CLV, NBO, risk score, segments
Digital / EventsBehavioral data, app sessions, interactions
Documents / RAGUnderwriting docs, claim evidence, correspondence
Architecture Pattern
Customer Profile הוא Virtual Profile — לא טבלה אחת גדולה. כל use-case מקבל profile view דרך API שמרכיב את הנתונים הרלוונטיים בלבד. No denormalization, no data duplication
Profile-per-Use-Case — API Design
GET /profile/service/{customer_id}
→ identity + active_policies + open_claims
  + last_interactions + service_flags

GET /profile/underwriting/{customer_id}
→ identity + policy_history + claim_history
  + risk_score + behavioral_indicators

GET /profile/marketing/{customer_id}
→ identity + CLV + churn_score + NBO
  + segments + consent + channel_preferences

GET /profile/digital/{customer_id}
→ identity + active_products + alerts
  + personalization_tokens
למה לא "טבלת לקוח אחת"
לקוח ביטוחי קשור לעשרות פוליסות, תביעות ותפקידים. טבלה שטוחה = מאות עמודות, thousands of NULLs, קושי לשמור SCD-2, ו-schema fragility. Entity model + composition API הוא הפתרון הנכון
AI Platform
ML & AI Platform — Classical + GenAI + Agentic
שלוש שכבות AI שנשענות על אותה תשתית דאטה — Feature Store ← Gold, Knowledge ← Vector Store
Classical ML Platform
Pricing, Churn, Fraud, Underwriting, Forecasting
  • → Feature Store — centralized, versioned, served from Gold
  • → Training — Dataiku On-Prem (existing compute)
  • → MLOps — experiment tracking, model registry, CI/CD
  • → Model Governance — version, lineage, bias monitoring
  • → Serving — batch scoring to Gold / real-time inference API
GenAI Platform
AI Assistants, Document Intelligence, Customer Service AI, Transcription
  • → LLM Gateway — single entry point, rate limiting, cost tracking
  • → Prompt Management — versioning, A/B, evaluation
  • → Orchestration — LangChain / LangGraph for chains & agents
  • → Guardrails — output validation, PII filtering, hallucination detection
  • → Observability — token usage, latency, quality metrics
Agentic AI Layer
Multi-step workflows, autonomous task execution, human-in-the-loop
  • → Agent Framework — tool-calling, state management
  • → Tool Library — ODS APIs, Customer Profile, Document Retrieval
  • → Workflow Engine — approval gates, escalation paths
  • → Audit Trail — כל פעולת agent נשמרת ומנוטרת
  • → Use cases: Underwriting Copilot, Claims Assist, KB Agent
Dataiku On-Prem — מיקום בארכיטקטורה
Dataiku On-Prem מתאים ל-Classical ML training (ניצול compute קיים, עלות נמוכה, proximity לדאטה). לא מתאים ל-GenAI / LLM inference (דרישות GPU ו-compute scale). המלצה: הרחבת Dataiku ל-Feature Store + MLOps, ובמקביל הקמת GenAI Platform בענן מנוהל
Vector & RAG
Vector & RAG Layer — Unstructured Knowledge
הפיכת מסמכים, תמלולים ונהלים ארגוניים ל-knowledge base שמודלי AI יכולים לצרוך בצורה מדויקת ומבוקרת
Pipeline — מסמך ל-Vector Store
1. Document Ingestion
PDF, Word, Transcriptions, HTML → normalized text. OCR לסרוקים. PII detection ו-redaction
2. Chunking Strategy
Semantic chunking (לא fixed-size). Overlap בין chunks. Metadata enrichment: document_type, date, domain, source
3. Embedding & Indexing
Embedding model (multilingual — תמיכה בעברית). Vector Store: Pinecone / Weaviate / pgvector. Hybrid search: dense + sparse (BM25)
4. Retrieval & RAG
Query → embedding → top-k retrieval → re-ranking → LLM generation. Context window management. Citation tracking

Hybrid
Hybrid Architecture — מיקום כל רכיב
לא "all-in cloud" ולא "all On-Prem". כל רכיב ממוקם לפי: compute cost, latency, data sensitivity, proximity to core
רכיב On-Prem Hybrid Cloud המלצה & נימוק
Core Systems נשאר On-Prem — legacy, regulatory, proximity
CDC / Ingestion Debezium On-Prem → Kafka Hybrid / Cloud. CDC agent קרוב לליבה
Data Lakehouse Cloud preferred (S3/ADLS + Databricks). Hybrid אם אבטחת מידע מחייבת
MDM קרוב לליבה לרזולוציה, אך חייב להיות חלק מ-data platform
ODS / Serving Cloud מועדף לסקייל ו-API. On-Prem אם כל הצרכנים פנימיים
Classical ML (Dataiku) נשאר On-Prem — existing compute, cost efficiency לtraining
GenAI / LLM ענן מנוהל — דרישות GPU, model updates, scale. Azure OpenAI / AWS Bedrock
Vector Store / RAG תלוי ברגישות המסמכים. Hybrid עם access control layer
CDP / Activation SFMC בענן. Decisioning layer — יכול להיות On-Prem / cloud
FinOps Principles
הענן יקר רק אם לא מנוהל נכון. עקרונות: (1) CDC ו-Incremental Processing במקום Full Load מקטינים compute cost ב-60-80%. (2) Storage/Compute separation — scale independently. (3) ML Training On-Prem → Inference Cloud (best of both). (4) FinOps dashboard + budget alerts per workload

Summary
The Platform Play — סיכום ארכיטקטוני
מה אנחנו בונים, למה, ואיך זה משתלב לכדי פלטפורמה שמפעילה את הארגון
Lakehouse
מנוע העיבוד. Bronze → Silver → Gold. מפריד Core מ-Consumption. Single source of truth לכל Data Products
MDM & Identity
Golden Record. Entity Graph. Identity Resolution. הבסיס לכל מה שמגיע אחריו — בלי MDM אין Customer 360
ODS — Serving Layer
מנוע התגובה. API-first, low-latency. מנגיש current-state לכל מערכות הקצה — מוקדים, דיגיטל, CRM
Customer Profile
Composition Layer. לא מקור — מחבר. Profile-per-use-case API. מבוסס MDM + Gold + ODS + AI
ML & AI Platform
Classical ML ב-Dataiku On-Prem. GenAI Platform בענן. Feature Store מ-Gold. Vector/RAG לידע לא מובנה. Agentic workflows
CDP & Activation
Audience → Decisioning → Journey. Real-time triggering. Contact Policy. SFMC לביצוע. NBA/NBO models
The Core Shift
מ: Data כ-by-product של מערכות הליבה, ETL כבדים, DWH ספריים, פרופילים מקומיים
ל: Data כ-Strategic Asset, Event-driven platform, Unified Business Models, AI-ready by design
Key Success Factors
(1) Executive sponsorship — CTO owns the platform, not a specific project. (2) Platform Team — dedicated, cross-functional, not embedded in domains. (3) Data Product mindset — domains own their data products with SLAs. (4) Thin vertical slices — production value at each phase, not a 3-year big-bang
